# Code and practice review, October 2026

A review of the whole project against what the beeb-port-kit (`..\beeb-port-kit`) learned from Paradroid, Edge Grinder, 1942 and Stryker's Run. Stryker's Run is the closest analogue (a BBC original rebuilt byte for byte, then enhanced; kit `PORTING.md` §2.1c). Line numbers are as of `ccc4169`. Defects already in [bugs.md](bugs.md) aren't repeated.

Every engine fix below is inside an SWRAM `IF` block or the build scripts, so none of them should move the original build off CRC `6389c446`. Confirm that with item 1 in place.

Effort: S = an hour or two, M = a day or so, L = several days.

## 2. Bugs found in this review (SWRAM build)

Not checked in an emulator; the first five were confirmed by reading the code.

| # | Bug | Where | Effort |
|---|---|---|---|
| 2.1 | **Thrust particle `ROR particles_dy_FRAC` is missing `,X`.** It shifts player bullet slot 0 every thrusting frame, and the exhaust dy is never halved. | `:10924` | S |
| 2.2 | **Fuel tractor counters: `LDX #$0B` clears 12 slots; SWRAM levels have 32.** A fuel cell in slot 12 or above can start pre-counted and be collected in one frame. Use `LEVEL_MAX_OBJECTS` under `IF`. | `:7648` | S |
| 2.3 | **Teleporter vs death and countdown.** Contact doesn't check `pod_destroying_player_timer`, so a ship dying that frame warps and keeps its life. `level_reset` sets `planet_countdown_timer = $FF`, so warping during the reactor countdown cancels it. Refuse contact unless both are idle. | `:12134`, `:6940` | S |
| 2.4 | **Up-facing laser beams can plot into code.** The no-clip path lets `end_y` reach 0, and y 0-15 maps to `$3800-$3C7F`, where `hide_landscape`, `draw_player_timed_to_vsync` and `test_inkey` live. Clip beams to y ≥ 32 (the top of the playfield). | `laser_range_y_up` ~`:11440` | S |
| 2.5 | **Sideways RAM banks hard-coded** (`SWRAM_BANK = 4`, `SPRITE_BANK = 5`). On a Model B without RAM in slot 4 the copy writes to ROM and the game crashes; with a ROM image in bank 4 the MOS still calls its stale `&8003`. Use kit `lib/swram_probe.6502` from `!BOOT` and zero `&02A1+bank`. Kit: `hardware-facts.md` §5. | `:10781` | M |
| 2.6 | **Level data is modified in place and never restored.** It's copied to SWRAM once at boot; `set_param` / `xor_param` and the mine position writes carry into the next game. Fixed by 4.1. | `:12708-12790` | (4.1) |
| 2.7 | **`action_destroy` on a door ($11) reads past the per-type tables**, which stop at $10. That gives explosion type $75 and score $20. Add the door entries, an `ASSERT` on each table's length, and block the target in the editor. | `:1460-1492` | S |
| 2.8 | **Door edge cases.** The on-screen test `< $F1` lets doors taller than 15 rows wrap into the ring; use `CLC; ADC width; BCS off`. Width 0 (reachable via `set_param`) writes 256 rows. `open_compare` uses `BNE`; use `BCS` so lowering the max mid-open can't run away. | `:12907` | S |
| 2.9 | **Bands vs invisible landscape.** `update_active_band` runs after `hide_landscape`, so a band change flashes the hidden terrain. `show_landscape` restores the level colour, not the band's. | `:10056` | S |
| 2.10 | **Unpause with `_FRIENDLY_KEYS` only works with CAPS LOCK on** (compares `$4F`). Fold case with `AND #$DF`. | `:99`, pause code | S |
| 2.11 | **Editor: no cap on objects per level.** Placement and export never check `LEVEL_MAX_OBJECTS` (32); a 33rd object overruns every per-object array. | `level_editor.py:3220, 3278, 5208` | S |

## 3. Frame rate

The game drops from ~33 to ~25 fps when scrolling with the pod. These are the cheap wins, in order.

| # | What | Why | Effort |
|---|---|---|---|
| 3.1 | **Carry the frame-gate remainder.** `draw_player_timed_to_vsync` waits until the clock reaches 3 cs, then zeroes it, so a 3.01 cs frame costs 4 cs. Subtract 3 (clamped) instead of zeroing, behind a flag. The average speed then stays near 33 Hz when the work hovers around the budget. | `:10192-10233` | S |
| 3.2 | **Turn off the MOS keyboard scan during play.** Controls are already read straight from the System VIA (`test_inkey`), but the MOS still scans every 10 ms while a key is held. The kit measured that at ~6% of CPU (`hardware-facts.md` §6). Disable it with OSBYTE `&B2` in `tick_loop`, and re-enable it for pause (OSRDCH) and the demo's OSBYTE `&81` poll. | `tick_loop`, `:4607` | S-M |
| 3.3 | **Debris emitter: shifts, not multiplies.** The direction factors are r, r/2, r/4, and ×16 is four shifts. That takes ~1.5-1.9k cycles per emit down to ~400. Also skip emitting when the well or pad is off-screen, and fix the slot-parity bias (odd slots emit twice as often). | `well_emit_debris_particle` | S |
| 3.4 | **Per-type object lists.** `update_all_laser_beams`, `tick_doors` and the gravity-well loop each walk all 32 objects (~27 cycles each): up to ~2.5k cycles a frame on levels with none of those types. Build index lists at level init. | | S-M |
| 3.5 | **Lost vsyncs.** `irq1_handler` passes vsync on to the MOS too; the kit measured ~1.2% of vsyncs lost that way, which shows as an unsynced ship draw. Mask the MOS vsync event (OSBYTE `&E9`). | `:5943` | S |
| 3.6 | Later, if needed: replace OSWORD 7 / ENVELOPE sound with kit `lib/sfx50.6502` + `sfx50.py`. That took MOS sound from ~16% of CPU to 2.2% in Stryker's Run. | | L |

**Not recommended: CRTC hardware scroll.** The 17,280-byte screen isn't a CRTC wrap size. A 20K screen would cost 3.2K of main RAM (only `&1A8` is free), the status bar would need a split, and terrain drawing already redraws only what changed. 3.1 and 3.2 address the same symptom for a fraction of the work.

## 4. Memory: the real limit on Thrust Next

Main RAM has `&1A8` bytes free in the SWRAM build. The sideways RAM payload travels inside the single `Thrust` file, so its true ceiling is ~`&A02` free, not the `&1F68` the build prints (`GUARD` at `:13860`).

| # | What | Where | Effort |
|---|---|---|---|
| 4.1 | **Per-level object workspace in SWRAM.** `initialise_level_pointers` is 969 bytes of main RAM, mostly ~45 copies of the same 7 array patches. At level start, copy the current level's 7 object columns (224 bytes) into one fixed SWRAM workspace and patch the original sites once. That frees ~800 bytes of main RAM and fixes 2.6. | `$2A06-$2DCF` | M |
| 4.2 | **Load the SWRAM bank as its own file** with kit `lib/loader.6502` (`load_bank`), as the TODO at `:10834` already suggests. That lifts the payload ceiling to the full bank. | `:10834-10841` | M |
| 4.3 | **Stop copying the 1,152-byte `skip &480` of zeros.** Start the COPYBLOCK at `&8480`. | `:10841` | S |
| 4.4 | **Move native-RAM `IF` bodies into SWRAM behind one `JSR` each:** checkpoint block (`:7009-7069`), mine contact (`:1837-1896`), type dispatch (`:1670-1720`). Wrap the unreachable legacy door routines (`:3523-3700`) in `IF NOT _SWITCHES`. | | M |
| 4.5 | **Generate a memory map from the build** (`-d` symbol dump) and use kit skill `beeb-ram-hunt` when space runs out. | | S |

## 5. Decide or delete

- **`_FAST_SPRITES`.** Nothing loads the `"Sprites"` file into bank 5 (`:14043`), and its data has no `skip &480`, so off-screen ship writes would corrupt it. Add the mirrored-frame offset from bugs.md and it's three problems deep. Either finish it with 4.2 or remove it along with `generate_ship_streams.py` and the 78K `ship_twostream_data.asm`.
- **Copy protection in the SWRAM build.** The `BYTEV+1` check (`app_init.asm:570`) scrambles the now-unencrypted image if any RAM utility hooks OSBYTE. Remove it under `_SWRAM_BUILD`, together with the dead bytes at `L3C77` (`:10746`). Load at `&FFFF1A00` so a second processor doesn't receive it over the Tube.

## 7. Practices and kit skills to adopt

The kit is copied rather than linked (`lib/README.md`, "fork-and-hack"). Its `lib/*.6502` files are written for Baron, so use the BeebAsm conversion in `docs/toolchain-baron.md`, or the BeebAsm versions at kit commit `5355d03`.

**Adopt:**
- **beeb-identical-build:** item 1.1. Also compare the `Thrust` file itself (`dfs.py compare --ignore INFO`), not just the whole-disc CRC, so adding a build stamp doesn't break the anchor.
- **jsbeeb MCP + beeb-smoke-test:** copy `template/.mcp.json`. A headless boot of each image that reaches the main loop on all six levels catches an editor export that assembles but crashes. `template/tools/harness.mjs` expects `<disc>.symbols.json`, so convert the label dump to that.
- **beeb-frame-drops / beeb-cycle-timing:** measure against the 3 cs gate (`debug_frame_time_cs`), not 50 Hz fields. Use them to put measured numbers in the two performance docs, which are currently hand-counted.
- **Release flag + build stamp** (`lib/boot_stamp.6502`, `beeb-release`): the shareable SWRAM build has `_DEBUG_FRAME_TIME` on, and `INITIAL_LEVEL` / `INITIAL_CHECKPOINT` (`:53-54`) have no guard. Under `RELEASE`, assert that the debug flags are off and the defaults are in place, and write an `INFO` file naming the flags. Then use **beeb-publish-wip** for shareable discs.
- **beeb-doc-pass** and a **`docs/decisions.md`**: the plan docs already carry status lines (the kit's brief convention). What's missing is a numbered decision log for each deviation from the original; the flag block can index it. Prefer labels over hard line numbers in docs, since numbers drift.
- **Relocation proof (PORTING §2.1c steps 5-9), when time allows:** build SWRAM with every gameplay flag off and run it side by side with the original using `template/tools/pairlock.mjs`, fed by the demo's key script. This catches behaviour changes caused only by code moving. Effort L.
- **beeb-bss-bugs** for Model B vs Master sideways RAM, **beeb-ram-hunt** for 4.x, **beeb-dataflow** via `beebasm_dataflow.py` for tracing state across the feature flags.

**Skip:**
- `irq.6502`, `sfx50.6502` (until 3.6), `keydown.6502` (`test_inkey` already does the same thing), `zx0`/`zx02`, `qdisc*`, `nmos.6502`, `break.6502`.
- beeb-arcade-capture, beeb-rom-model-probe, beeb-buffer-oracle (software scroll), beeb-sound-verify, beeb-key-numbers, beeb-start-port, beeb-portable-build, and beeb-micro-grind (it needs a test suite as its gate first).
- The C64/CPC/MAME tools.
